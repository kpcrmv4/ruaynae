**ยังไม่ได้ตั้งงาน pg_cron ให้เรียก `sweep-orphans`** — pg_net ต้องยิงไปที่ URL
สาธารณะ ซึ่งจะมีก็ต่อเมื่อ deploy แล้ว · ตั้งตอนนี้ = งานที่ยิงไปที่ที่ไม่มีอยู่
แล้ว log error ทุกชั่วโมง · endpoint ทำงานถูกต้องแล้ว (พิสูจน์ที่ `P2-R2-09/10`)
เหลือแค่ตั้งเวลาให้ตอน deploy — ใส่ไว้ในเช็คลิสต์ก่อน deploy

**หลักฐาน:** `verify-txn.mjs` (32) · `verify-slips.mjs` (12) · `verify-ledger.mjs` (8) · `verify-money.mjs` (9) — อยู่ใน `npm run verify:all`

**สิ่งที่ตารางแถวนี้จับได้ตั้งแต่วันแรก** — `P2-DB-04` แดงในการรันครั้งแรก:
หัวหน้าไซต์ยิง `PATCH status=approved` แล้วได้ **200 สำเร็จ** ทั้งที่สถานะไม่เปลี่ยน
· ต้นเหตุคือไม่มีอะไรเติม `created_by` เลย ค่าเป็น `null` เงื่อนไข
`created_by = auth.uid()` ในทุก policy จึงเป็น `null` ไม่ใช่ `true` →
RLS มองไม่เห็นแถวสำหรับ UPDATE → โดน 0 แถว → PostgREST ตอบ 200
**สาขานั้นของทุก policy ตายสนิทโดยไม่มีอะไรฟ้อง** — กฎที่เขียนไว้สวยงามแต่เป็นจริงไม่ได้
· แก้ด้วยการเติมใน trigger (ไม่ใช่ `default` ซึ่ง client ส่งค่าทับได้ → `P2-DB-20`)

**red-test ที่ทำไปแล้ว**
- ทิ้ง unique index ของ `client_ref` → **P2-API-08 แดง**: ยิงพร้อมกันสองครั้ง
  ได้ **2 แถว** (เงินถูกนับซ้ำ) · คืน index แล้วได้ 1 แถวและทั้งคู่ตอบ 201/200

**สามอย่างที่เฟสนี้พังง่ายที่สุด**
1. **`0 === 0`** — ยอดที่หน้าจอ ยอดที่ RPC และยอดที่ SQL ตรงกันหมดที่ศูนย์
   โดยไม่ได้พิสูจน์การบวกสักครั้ง · ทุกแถว P2-CALC ต้องสร้างข้อมูลจริงก่อน
2. **ไฟล์กำพร้า** — อัปขึ้น R2 สำเร็จแล้วบันทึกแถวไม่สำเร็จ ไฟล์ค้างตลอดไป
   ไม่มี error ที่ไหนเลย · ทางที่ล้มเหลวคือทางที่สร้างขยะ และเป็นทางที่ไม่มีใครทดสอบ
3. **RLS ปฏิเสธการเขียนแบบเงียบ ๆ** — `update`/`delete` ที่โดน 0 แถวไม่ใช่ error
   PostgREST ตอบว่าสำเร็จ · ทุก route ต้องอ่านแถวกลับมาดูว่ามีจริง
