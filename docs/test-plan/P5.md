# P5 · เบิกล่วงหน้า + รอบจ่ายค่าแรง — ตารางตรวจรับ

> เขียน**ก่อน**โค้ด ตาม `kp-acceptance-test-matrix`
> `tsc` เขียวและ `next build` เขียว **ไม่นับ**เป็นหลักฐานของแถวใดในนี้

**สถานะ:** `☐` ยังไม่ตรวจ · `✅` ผ่านโดยมีคำสั่งรันได้รองรับ · `❌` ตก · `⚠️` blocked · `👤` ต้องคนตรวจ

> 🔴 **กฎที่ทั้งเฟสนี้มีอยู่เพื่อรักษา** (DESIGN.md §5.4)
> ติ๊กคนเข้าไซต์ = **ต้นทุนเกิด** (accrual) · เบิกล่วงหน้าและปิดรอบจ่าย = **เงินสดออก**
> ทั้งสองอย่างนี้ **ห้ามบวกกันเป็นต้นทุน** ไม่งั้นต้นทุนเป็นสองเท่าทันที
>
> ตัวอย่างที่ต้องถูก: สมพงษ์ทำงาน 6 วัน × ฿550 = **ต้นทุน ฿3,300**
> เบิกล่วงหน้า ฿1,000 → ต้นทุน**ไม่ขยับ** · ปิดรอบจ่ายอีก ฿2,300 → ต้นทุน**ไม่ขยับ**
> รวมต้นทุน ฿3,300 · เงินสดออก ฿3,300 · ค้างจ่ายเหลือ ฿0
>
> 🔴 **เจ้าของเท่านั้นทั้งเฟส** — คำสั่งเจ้าของ 31 ส.ค. 2569 ว่าหัวหน้าไซต์
> มีหน้าที่แค่บันทึกรายจ่ายและบันทึกว่าใครมาทำงาน · เบิกและรอบจ่ายเป็นเรื่องเงิน

  — นี่คือ "ต้นทุนบวกซ้ำ" กับดักข้อ 1 ของโปรเจ็คนี้ ในรูปแบบที่ตัวเลข
  ยังดูสมเหตุสมผลจนกว่าจะเอาไปเทียบกับที่จ่ายจริง

**กฎการติ๊ก** — แถวที่ ID มี `-DB-` `-API-` ต้องมี ID อยู่ใน label ของ check ที่รันได้จริงใน
`scripts/**` · ติ๊กจากความจำไม่นับ · กระทบยอดด้วย `node scripts/verify-matrix.mjs`

**สามอย่างที่เฟสนี้พังง่ายที่สุด**

1. **ต้นทุนบวกซ้ำ** — เบิกล่วงหน้าและปิดรอบจ่ายคือเงินสดออก **ไม่ใช่ต้นทุน**
   · `P5-DB-10` และ `P5-DB-11` คือแถวที่จับเรื่องนี้ และต้องวัด `cost_total`
   **ก่อนและหลัง** ไม่ใช่ดูว่าเลขสุดท้ายดูสมเหตุสมผล
2. **เพดานเบิกที่เทียบทีละใบ** — เบิก ฿2,000 สองครั้งบนค้างจ่าย ฿3,300 ผ่านทั้งคู่
   ถ้า trigger ไม่บวกยอดที่เบิกไปแล้วเข้าไปด้วย · `P5-DB-03` คือแถวนั้น
3. **ตัวเลขที่จ่ายเงินไปแล้วเปลี่ยนย้อนหลัง** — แก้ `wage_snapshot` หรือลบ
   `attendance` ของรอบที่ปิดแล้ว ทำให้ยอดที่จ่ายไปกับยอดที่ระบบคำนวณไม่ตรงกัน
   ตลอดไป โดยไม่มี error · `P5-DB-13`/`P5-DB-14`

**ยังไม่ทำในเฟสนี้:** ปันส่วนเงินเดือนของคนรายเดือนเข้าไซต์ตามจำนวนวัน (เฟสหลัง)
· เงินเดือนของคนรายเดือนยังไม่เข้ารอบจ่ายรายวัน — ตัดสิ้นเดือนแยกต่างหาก
