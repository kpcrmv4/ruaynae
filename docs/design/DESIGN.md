## 1. ผลิตภัณฑ์

เว็บแอปสำหรับผู้รับเหมาก่อสร้างรายเล็ก-กลาง ใช้บันทึกรายรับ-รายจ่ายรายวันของแต่ละโครงการ
พร้อมแนบสลิป/บิล จัดการพนักงานและค่าแรง และให้เจ้าของเห็นภาพรวมว่าแต่ละโปรเจ็คคืบหน้าแค่ไหน
เก็บเงินได้เท่าไหร่แล้ว และเหลือกำไรเท่าไหร่

**ขอบเขตระบบ:** บริษัทเดียว (single-organization) ไม่ใช่ SaaS หลายผู้เช่า
ไม่มีหน้าสมัครสมาชิก — แอดมินเป็นคนสร้างผู้ใช้ให้

## 2. ผู้ใช้และสิทธิ์

| Role | ล็อกอินด้วย | เห็นอะไร | ทำอะไรได้ |
|---|---|---|---|
| **เจ้าของ / แอดมิน** (`owner`) | อีเมล + รหัสผ่าน | ทุกโครงการ ทุกตัวเลข กำไร ประวัติการแก้ไข | ทุกอย่าง — อนุมัติ/ตีกลับรายจ่าย ปิดรอบจ่ายค่าแรง CRUD พนักงาน/โครงการ/ผู้ใช้ |
| **หัวหน้าโครงการ** (`site_supervisor`) | PIN 6 หลัก (แป้นตัวเลข) | เฉพาะโครงการที่ตัวเองดูแล ณ ช่วงเวลานั้น | คีย์รายจ่ายของโครงการตัวเอง (เข้าคิวรออนุมัติ) · ลงชื่อคนเข้าโครงการ · บันทึกเบิกล่วงหน้าให้ลูกน้อง |

**คนงานไม่ได้ล็อกอินเข้าระบบ** — เป็นข้อมูลใน `employees` เฉย ๆ มีเจ้าของหรือหัวหน้าโครงการเป็นคนคีย์ให้

## 3. โทนและบุคลิก — "Navy & White"

น้ำเงิน-ขาว เรียบ ทางการ อ่านง่าย · การ์ดโปร่ง ตัวหนังสือใหญ่ (ไม่ใช่ตารางแน่น)
เพราะผู้ใช้หลักคือหัวหน้าโครงการบนมือถือกลางแดด และผู้ใช้ยังไม่ชำนาญคอมพิวเตอร์

**เหตุผลที่เลือกค่าสีแบบนี้** — `#1D4ED8` เข้มพอที่จะทำหน้าที่ได้ทั้งสองอย่างด้วยค่าเดียว:
เป็นสีตัวหนังสือบนพื้นขาว (6.70:1) และเป็นพื้นปุ่มที่มีตัวหนังสือขาวทับ (6.70:1) ผ่าน WCAG AA ทั้งคู่
sidebar เป็น **กรมท่าเข้ม `#14264A` ไม่ใช่สีแบรนด์** เพราะแผงสีแบรนด์เต็ม ๆ คือสนามสีที่ใหญ่ที่สุดบนจอ
วางอยู่ตรงที่คนมองน้อยที่สุด แล้วแย่งความสนใจไปจากพื้นที่เนื้องาน

### 4.1 รีดีไซน์มือถือ (31 ส.ค. 2569 — คำสั่งเจ้าของ, ทับข้อ 4 เดิมเฉพาะที่ระบุ)

เป้าหมาย: **ใช้บนมือถือเป็นหลัก · เมนูต่อเนื่อง · เน้นการบันทึกประจำวัน** — ลอจิก สิทธิ์
และ endpoint เดิมทั้งหมด ไม่มีการแก้ฐานข้อมูล

**หน้าแรก = "วันนี้"** (เดิมคือ "ภาพรวม") — เปิดแอปแล้วเจอการ์ด **งานวันนี้** ก่อนตัวเลขสรุป:

| Role | แถวในการ์ดงานวันนี้ |
|---|---|
| เจ้าของ | รออนุมัติ (จำนวน + ยอด + เก่าสุดค้างกี่วัน) · คนเข้าโครงการวันนี้ (ลงแล้วกี่โครงการจากกี่โครงการ) · รายการเงินวันนี้ (เข้า/ออก) |
| หัวหน้าโครงการ | ลงชื่อคนเข้าโครงการ (ลงแล้วกี่คน) · บันทึกรายจ่าย (คีย์แล้วกี่รายการ · รออนุมัติกี่) · ตีกลับที่ต้องแก้ (โผล่เฉพาะเมื่อมี) |

ทุกแถวแตะแล้วไปหน้างานนั้นต่อได้ทันที — **ไม่มีตัวเลขที่เป็นทางตัน**
· แถบสถานะโครงการย่อเหลือ 3 ช่อง (กำลังก่อสร้าง/ใกล้ครบ/เลยกำหนด) เพราะยอดรออนุมัติย้ายขึ้นการ์ดงานวันนี้แล้ว

**แถบล่างจัดช่องตาม role** (ช่อง 5 = เพิ่มเติม เสมอ):

| Role | ช่อง 1 | ช่อง 2 | กลาง | ช่อง 4 |
|---|---|---|---|---|
| หัวหน้าโครงการ | วันนี้ | คนเข้าโครงการ | `[+]` | รายการ (`/ledger`) |
| เจ้าของ | วันนี้ | รออนุมัติ (ตัวเลขแดงค้าง) | `[+]` | รายการ (`/ledger`) |

**ปุ่มกลาง `[+]` เปลี่ยนจากลิงก์ตรงเป็นแผ่น "บันทึกประจำวัน"** — ทุกการบันทึกที่ทำทุกวัน
อยู่ห่างไม่เกิน 2 แตะจากทุกหน้า: บันทึกรายจ่าย · บันทึกรายรับ (เจ้าของ) ·
ลงชื่อคนเข้าโครงการ · เบิกล่วงหน้า (เจ้าของ → `/payroll`)
· แผ่น "เพิ่มเติม" มีการ์ดผู้ใช้ + ปุ่มธีม + ออกจากระบบ

**จังหวะบันทึกต่อเนื่อง** (ลอจิกบันทึกเดิม แต่งจังหวะใหม่):
- ฟอร์มบันทึก: หมวดเป็น**ชิปแตะเลือก** ไม่ใช่กล่องเลือก · จ่ายด้วยเป็น 2 ปุ่ม ·
  ปุ่มบันทึก**ลอยเหนือแถบล่าง**พร้อมยอดเงินบนปุ่ม · บันทึกเสร็จโฟกัสกลับช่องยอดเงิน
  (โครงการ/หมวด/วันที่/วิธีจ่ายค้างไว้) และมีลิสต์ "วันนี้คีย์แล้ว n รายการ" ใต้ฟอร์มพร้อมสถานะ
- คนเข้าโครงการ: ปุ่ม **"เหมือนเมื่อวาน — ลงชื่อ n คนเดิม"** (ยิง API เดิมทีละคน กติกากันซ้ำ
  ของฐานข้อมูลตรวจครบ · คัดลอกเฉพาะเต็ม/ครึ่งวัน ไม่คัดลอก OT) + **แถบสรุปลอยล่าง**
  (จำนวนคน · ค่าแรงเฉพาะเจ้าของ · ยังไม่เข้ากี่คน)
- คนเข้าโครงการ · **ป้ายบอกคนที่ไปอยู่โครงการอื่นแล้ววันนี้** (ตามเดโม่ที่อนุมัติ: แถวสีเทา
  พร้อมข้อความ "วันนี้อยู่โครงการ…") — เพดานคือ **1 วันต่อคนต่อวัน** บังคับที่ guard trigger
  · เต็มวันแล้ว = แถวเทา ป้าย "ลงครบวันแล้ว" ไม่มีปุ่มให้กด · ครึ่งวันแล้ว = ป้าย
  "ลงได้ครึ่งวัน" และระบบส่ง `0.5` ให้เอง (ช่องครึ่งวันหายไป เพราะเลือกอย่างอื่นก็ถูกปฏิเสธ)
  · ปุ่ม "เหมือนเมื่อวาน" ไม่นับและตัดยอดให้พอดีโควตาที่เหลือ
  🔴 นี่คือ**คำแนะนำ ไม่ใช่การควบคุม** — หัวหน้าโครงการเห็นเฉพาะโครงการที่ตัวเองดูแลตาม RLS
  คนที่ไปอยู่โครงการของคนอื่นจะยังไม่มีป้าย และถูกปฏิเสธที่ฐานข้อมูลเหมือนเดิม
  · ห้ามเอาป้ายนี้ไปแทน guard ที่ฐานข้อมูลเด็ดขาด
- รออนุมัติ: ปุ่มอนุมัติ/ตีกลับเต็มแถวบนจอเล็ก (อนุมัติช่องใหญ่กว่า) · รูปสลิปใหญ่ขึ้น ·
  บอก "ค้าง n วัน" ต่อรายการ (แดงเมื่อ ≥ 2 วัน)
- รายรับ-รายจ่าย: จัดกลุ่มตามวัน (วันนี้/เมื่อวาน/วันที่) พร้อม**ยอดสุทธิของวัน**
  (ไม่รวมตีกลับ · กลุ่มที่ถูกตัดด้วย pagination ไม่โชว์ยอด — ยอดครึ่งวันแย่กว่าไม่มียอด)

**ปุ่มลัดบนหน้ารายละเอียดโครงการ** (คำสั่งเจ้าของ 31 ส.ค. 2569) — เปิดหน้าโครงการแล้วงานถัดไป
เกือบทุกครั้งคือ "บันทึกของโครงการนี้" เดิมต้องถอยออกไปเมนูรวมแล้วเลือกโครงการเดิมซ้ำ
· แถวปุ่มอยู่ใต้หัวเรื่อง: **บันทึกรายจ่าย · บันทึกรายรับ (เจ้าของ) · ลงชื่อคนเข้าโครงการ · รายการของโครงการนี้**
ทุกปุ่มพาไปหน้าเดิมของระบบพร้อมโครงการนั้นถูกเลือกไว้ให้ (`/entry?site=` · `/attendance?site=` · `/ledger?site=`)

🔴 **ปุ่มโผล่เฉพาะสถานะที่ปลายทางรับโครงการนั้นได้จริง** — กล่องเลือกโครงการของ `/entry` มีแค่
`planning/active/paused` และของ `/attendance` มีแค่ `active/planning` · โชว์ปุ่มบนโครงการที่ปิดงานแล้ว
= กดไปแล้วเด้งไปโครงการอื่นเงียบ ๆ แล้วคนคีย์ลงผิดโครงการโดยไม่มีอะไรเตือน
· `?site=` ฝั่งเซิร์ฟเวอร์ต้องตรวจว่าอยู่ในลิสต์ที่ RLS คืนมาจริงก่อนใช้ ไม่เชื่อค่าจาก URL

🔴 **ตัวกรองที่มองไม่เห็นคือตัวกรองที่ทำให้คนอ่านตัวเลขผิดขอบเขต** — `/ledger?site=`
ต้องขึ้นแถบบอกว่ากำลังดูเฉพาะโครงการไหน พร้อมปุ่ม "ดูทุกโครงการ" · และชิปสถานะ/ช่องค้นหา
ต้องพา `site`/`kind`/`from`/`to` ไปด้วย (prop `extra` ของ `ListToolbar`)
ไม่งั้นกดชิปทีเดียวขอบเขตเปลี่ยนจากโครงการเดียวเป็นทั้งบริษัทโดยไม่มีอะไรบอก

### 4.2 หน้ารายงาน `/reports` (คำสั่งเจ้าของ 31 ส.ค. 2569)

**เจ้าของเท่านั้น** — ทุกตัวเลขในหน้านี้เป็นเงิน ซึ่งเป็นของเจ้าของตามที่ตัดสินใจไว้ตอน P4.5

ตัวกรอง: **รายเดือน / รายปี** + เลือกโครงการ (หรือทั้งบริษัท) · สถานะอยู่บน URL (`?p=2026-08&site=…`)
แชร์ลิงก์ได้ กดย้อนกลับได้ · ทุกช่วงเทียบกับช่วงก่อนหน้าอัตโนมัติ (เดือนก่อน / ปีก่อน)

| ส่วน | สิ่งที่แสดง |
|---|---|
| แถบสรุป | รายรับ · ต้นทุนที่เกิดขึ้น · กำไรขั้นต้น พร้อม % เทียบช่วงก่อน |
| กราฟเงินเข้า–ออก | แท่ง**ขึ้น**=รายรับ · แท่ง**ลง**=ต้นทุน (แยกท่อนรายจ่าย/ค่าแรง) รายวันเมื่อดูรายเดือน · รายเดือนเมื่อดูรายปี |
| ต้นทุนแยกหมวด | แท่งแนวนอน + % ของต้นทุนรวม · **มีแถว "ค่าแรงจากการลงชื่อ" ด้วย** เพื่อให้ผลรวมเท่ากับต้นทุนรวมพอดี |
| รายรับแยกหมวด | มัดจำ / งวดงาน / ค่างานเพิ่ม / อื่น ๆ |
| แยกตามโครงการ | รายรับ · ต้นทุน · ส่วนต่างของช่วงนั้น (ไม่ใช่กำไรทั้งโครงการ) รวมแถวส่วนกลาง |
| คนและค่าแรง | วันแรงรวม · จำนวนคน · ค่าแรงที่เกิดขึ้น · OT + คนที่ได้ค่าแรงสูงสุด |
| เงินสดออกฝั่งค่าแรง | เบิกล่วงหน้า · ปิดรอบจ่าย + วิธีจ่าย (เงินสด/โอน) |

🔴 **ทุกยอดรวมคำนวณในฐานข้อมูล** ผ่าน RPC `report_*` ทั้งหมด ไม่ดึงแถวมาบวกใน JS
(รายงานทั้งปีมีได้หลายพันแถว และ PostgREST ตัดที่ 1,000 เงียบ ๆ — §7)
· RPC ทุกตัวเป็น `security invoker` + `is_owner()` คนอื่นได้ **0 แถว** ไม่ใช่เลข 0

🔴 **สูตรเงินต้องเป็นตัวเดียวกับหน้าอื่น** — รายรับ = `approved` เท่านั้น ·
ต้นทุน = รายจ่าย `approved` + ค่าแรงจากการลงชื่อ · **เบิกล่วงหน้าและปิดรอบจ่ายมีช่องของตัวเอง
ห้ามบวกเข้าต้นทุน** (§5.4) — คิดผิดตรงนี้กำไรในรายงานจะไม่ตรงกับหน้าโครงการ แล้วคนดูจะเลิกเชื่อทั้งหน้า

🔴 **กราฟต้องอ่านได้โดยไม่ต้องพึ่งสี** — เขียว-แดงเป็นคู่ที่คนตาบอดสีแยกไม่ออกที่สุด
จึงให้ **ตำแหน่ง** (ขึ้น=เข้า / ลง=ออก) เป็นตัวแยกหลัก สีเป็นตัวเสริม พร้อมคำอธิบายสีและป้ายแกน
· กราฟเขียนเป็น SVG เอง ไม่เพิ่มไลบรารี และเป็น Server Component เต็มใบ (ไม่มี JS ฝั่ง client)

### 4.3 หน้าค่าแรง `/payroll` — สองมุมมอง (คำสั่งเจ้าของ 31 ส.ค. 2569)

สลับด้วยแท็บบน URL (`?tab=grid&p=2026-08`) เจ้าของเท่านั้น

**1) ค้างจ่ายรายคน** (ค่าเริ่มต้น) — แต่ละแถวบอกทั้ง **กี่วัน** และ **กี่บาท** ที่ค้าง
ยอดเงินอย่างเดียวตอบไม่ได้ว่าคนนี้มาทำงานกี่วัน ซึ่งเป็นตัวเลขที่ใช้เถียงกันจริงหน้างาน

**2) ตารางการทำงาน** — แถวเป็นคน คอลัมน์เป็นวันของเดือนที่เลือก (ค่าเริ่มต้น = เดือนปัจจุบัน)

🔴 **ตารางกว้างกว่าจอเสมอ** — เลื่อนแนวนอนในกล่องของตัวเอง คอลัมน์ชื่อคนตรึงไว้ซ้าย
ห้ามปล่อยให้ทั้งหน้าเลื่อน เพราะเชลล์ตั้ง `overflow-x: clip` ส่วนที่เกินจะถูกตัดทิ้ง
โดยไม่มีแถบเลื่อนบอก (§17 ข้อ 7)

### 4.4 ชวนติดตั้งแอปและเปิดแจ้งเตือน (คำสั่งเจ้าของ 31 ส.ค. 2569)

ลำดับที่ตั้งใจ: **ติดตั้งก่อน → แล้วค่อยขอสิทธิ์แจ้งเตือน**

ขอสิทธิ์แจ้งเตือนตอนเพิ่งเปิดเว็บครั้งแรกคือวิธีที่ทำให้คนกด "ไม่อนุญาต" มากที่สุด
และเบราว์เซอร์ **จำคำตอบนั้นไว้ถาวร** ขอใหม่ไม่ได้อีกเลยจนกว่าเจ้าตัวจะเข้าไปแก้
ในตั้งค่าของเบราว์เซอร์เอง — ซึ่งไม่มีทางเกิดขึ้นกับผู้ใช้กลุ่มนี้
ตอนที่คนเพิ่งกดติดตั้งคือตอนที่เขาตั้งใจจะใช้จริง จึงเป็นจังหวะที่ถามได้

**สามที่ที่เกี่ยวข้อง**

| ที่ | เห็นเมื่อไหร่ | ทำอะไรได้ |
|---|---|---|
| แบนเนอร์บนสุดของเนื้อหา | ยังไม่ติดตั้ง และยังไม่เคยกดปิด | กดติดตั้ง (Android/เดสก์ท็อป) · ดูวิธีทำ (iOS) |
| แบนเนอร์เดียวกัน หลังติดตั้งแล้ว | ติดตั้งแล้ว + แจ้งเตือนยัง `off` + ยังไม่เคยกดปิด | กดเปิดแจ้งเตือน |
| การ์ดในหน้า `/settings` | เสมอ | บอกสถานะ + ปุ่มติดตั้ง หรือขั้นตอนของ iOS |

🔴 **แบนเนอร์ปิดได้และจำไว้ → ต้องมีที่ที่กลับมากดได้เสมอ** ไม่งั้นคนที่เผลอกดปิด
จะติดตั้งไม่ได้อีกเลยจนกว่าจะล้างข้อมูลเบราว์เซอร์ · การ์ดในหน้าตั้งค่าคือที่นั้น
แบนเนอร์เป็นทางลัด ไม่ใช่ทางเดียว

🔴 **`beforeinstallprompt` ยิงครั้งเดียว และยิงก่อน React mount เกือบทุกครั้ง**
ถ้าให้แต่ละคอมโพเนนต์ดักเอง ตัวที่ mount ทีหลังจะไม่ได้ event เลย แล้วปุ่ม "ติดตั้ง"
จะหายไปโดยไม่มีใครรู้ว่าทำไม · `lib/pwa-install.ts` ดักตั้งแต่ตอน import แล้วแจก
ให้ทุกที่ผ่าน `useSyncExternalStore`

🔴 **iOS ไม่มี event นี้เลยตามการออกแบบของ Safari** — ห้ามโชว์ปุ่มที่กดแล้วไม่มีอะไรเกิดขึ้น
ต้องเขียนขั้นตอน ("แตะปุ่มแชร์ → เพิ่มไปยังหน้าจอโฮม") ให้อ่านแทน

🔴 **"เปิดแจ้งเตือนแล้ว" อ่านจาก `pushManager.getSubscription()` ของเบราว์เซอร์เสมอ
ไม่ใช่จากฐานข้อมูล** — คนหนึ่งคนใช้หลายเครื่อง อ่านจากฐานแล้วเครื่องที่ยังไม่ได้เปิด
จะโชว์ว่าเปิดแล้ว · และถ้าบันทึก subscription ฝั่งเราไม่สำเร็จ **ต้องถอน subscription
ทิ้งด้วย** ไม่งั้นหน้าจอบอกว่าเปิดแล้วทั้งที่เครื่องนั้นจะไม่มีวันได้รับ push
· ตรรกะทั้งหมดอยู่ที่ `lib/push.ts` ที่เดียว ทั้งการ์ดและแบนเนอร์เรียกตัวเดียวกัน

🔴 **สถานะที่เซิร์ฟเวอร์ไม่มีทางรู้ ให้อ่านผ่าน `useSyncExternalStore` ไม่ใช่
`useState` + `useEffect`** (ติดตั้งแล้วไหม · ปิดคำชวนไปหรือยัง · ธีมไหน)
— `setState` ตรง ๆ ใน effect คือเรนเดอร์สองรอบทุกครั้ง และ React 19 นับเป็น
cascading render · hook `useIsClient()` ใน `lib/use-is-client.ts` ใช้ร่วมกัน

การจำว่า "ปิดคำชวนไปแล้ว" เก็บใน `localStorage` **ไม่ใช่ฐานข้อมูล** เพราะเป็นความชอบ
ของ *เครื่องนี้* ไม่ใช่ของบัญชี — คนเดียวกันอาจติดตั้งบนมือถือแต่ไม่อยากติดตั้งบนคอมที่ออฟฟิศ
· และ `localStorage` อ่านไม่ได้ในโหมดส่วนตัวของบางเบราว์เซอร์ จึงห่อ try/catch ทุกครั้ง

## 5. กลไกหลักที่ตกลงกันแล้ว

### 5.1 ความคืบหน้าโปรเจ็ค — 3 แถบอัตโนมัติ
ตั้งแค่ **ชื่อโครงการ · ค่างานรวม · วันเริ่ม · วันจบ** แล้วระบบสรุปเอง:

| แถบ | สูตร | สี |
|---|---|---|
| เวลา | `(วันนี้ − วันเริ่ม) / (วันจบ − วันเริ่ม)` | `--bar-time` |
| เก็บเงินแล้ว | `Σ รายรับที่อนุมัติแล้วของโครงการ / ค่างานรวม` | `--bar-paid` |
| ต้นทุนที่จ่ายจริง | `Σ ต้นทุนที่อนุมัติแล้วของโครงการ / ค่างานรวม` | `--bar-cost` |

**กำไรคงเหลือ (ประมาณ) = ค่างานรวม − ต้นทุนที่เกิดขึ้นแล้ว**

เมื่อแถบต้นทุน (%) แซงแถบเก็บเงิน (%) ให้ขึ้นป้ายเตือน "ต้นทุนโตเร็วกว่าเงินที่เก็บได้" บนการ์ดโครงการ

**ไม่ต้องตั้งงวดล่วงหน้า** — เวลาบันทึกรายรับแค่เลือกว่าเป็น *มัดจำ / งวดที่ N / ค่างานเพิ่ม / อื่น ๆ*
ระบบนับเลขงวดให้เอง · แต่**ถ้าอยากตั้งแผนงวดล่วงหน้าก็ทำได้** (ตาราง `site_milestones`)
งวดที่ตั้งแผนไว้แต่ยังไม่เก็บจะโชว์เป็นแถวสีแบรนด์อ่อนต่อท้ายรายการงวด

### 5.2 รายจ่ายสองแบบ
- **ผูกโครงการ** (`site_id` มีค่า) — ค่าวัสดุ ค่าแรง ค่าเช่าเครื่องจักร ผู้รับเหมาช่วง ค่าขนส่ง
- **ไม่ผูกโครงการ / ส่วนกลาง** (`site_id IS NULL`) — ค่าน้ำมัน ค่าทางด่วน ค่าออฟฟิศ

ป้ายบอกประเภทต้องแยกออกจากกันในแวบเดียว: ผูกโครงการ = ชิปน้ำเงินขอบทึบ · ส่วนกลาง = ชิปขอบประ

### 5.3 การอนุมัติ
หัวหน้าโครงการคีย์ → `pending` → เจ้าของกด **อนุมัติ** (`approved`) หรือ **ตีกลับ** (`rejected` + เหตุผล)
รายการที่เจ้าของคีย์เองเข้าเป็น `approved` ทันที

**ตัวเลขในหน้าภาพรวมนับเฉพาะ `approved`** แต่ต้องโชว์ยอด "รออนุมัติ" แยกเป็นการ์ดของตัวเอง
ไม่ใช่ซ่อนหายไปเฉย ๆ

### 5.4 ค่าแรง — accrual ไม่ใช่ cash ⚠️
**นี่คือกฎที่พังง่ายที่สุดของทั้งระบบ**

- **ติ๊กคนเข้าโครงการ = ต้นทุนค่าแรงเกิดขึ้นทันที** (accrual) → เข้าต้นทุนโครงการ และเข้ายอด "ค้างจ่าย" ของคนนั้น
- **เบิกล่วงหน้า** และ **ปิดรอบจ่ายค่าแรง** คือ **การจ่ายเงิน ไม่ใช่ต้นทุน** — เป็นการล้างหนี้ที่เกิดไปแล้ว
  ถ้านับเป็นต้นทุนอีกรอบ ต้นทุนจะบวกซ้ำสองเท่า

ใน UI แถวพวกนี้ต้องขึ้นเป็นสีเทาพร้อมป้าย **"จ่ายเงิน · ไม่นับซ้ำเป็นต้นทุน"** ไม่ใช่ตัวเลขแดงเหมือนรายจ่ายทั่วไป

**ตัวอย่างที่ต้องถูก:** สมพงษ์ทำงาน 6 วัน × ฿550 = ฿3,300 → ต้นทุนโครงการ +฿3,300
เบิกล่วงหน้าไปแล้ว ฿1,000 → **ต้นทุนไม่ขยับ** เงินสดออก ฿1,000
ปิดรอบจ่ายอีก ฿2,300 → **ต้นทุนไม่ขยับ** เงินสดออก ฿2,300
รวมต้นทุน ฿3,300 · รวมเงินสดออก ฿3,300 · ยอดค้างจ่ายเหลือ ฿0 ✓

### 5.5 พนักงานรายวัน / รายเดือน
ตั้งได้รายคน (`wage_type`)

- **รายวัน** — ติ๊กเข้าโครงการแล้วคิดค่าแรงตามเรตของคนนั้น รองรับ **ครึ่งวัน** (`work_units = 0.5`) และ **OT** (จำนวนเงินตรง ๆ)
- **รายเดือน** — ติ๊กเข้าโครงการได้เพื่อบันทึกว่าอยู่ไหน แต่**ไม่คิดค่าแรงรายวัน** เงินเดือนตัดสิ้นเดือน
  แต่ละคนตั้งได้ว่าเงินเดือนลง **โครงการประจำ** (`default_site_id`) หรือ **ส่วนกลาง** (`NULL`)

**เรตค่าแรงต้องถูก snapshot ลงในแถว `attendance` ตอนบันทึก** ห้าม join ไปอ่านเรตปัจจุบัน —
ไม่งั้นวันที่เจ้าของขึ้นค่าแรงให้ใครสักคน ต้นทุนของงานที่ปิดไปแล้วเมื่อ 3 เดือนก่อนจะเปลี่ยนตามไปด้วยเงียบ ๆ

### 5.6 เบิกล่วงหน้า — มีเพดาน
`เพดานที่เบิกได้ = ค่าแรงค้างจ่ายสะสม − ที่เบิกไปแล้ว (ยังไม่หัก)`

บันทึกเกินเพดานต้องไม่สำเร็จ และต้อง**บังคับที่ฐานข้อมูล (trigger) ไม่ใช่แค่เช็คในหน้าจอ**
เพราะหน้าจอเป็นแค่คำแนะนำ ฐานข้อมูลเป็นความจริง

ตอนปิดรอบจ่าย ระบบหักยอดค้างเบิกอัตโนมัติ → `net_paid = accrued − advance_deducted`

### 5.7 ชื่อบริษัทและโลโก้ — ตั้งค่าได้ ไม่ได้ฝังในโค้ด

แก้จากหน้าตั้งค่า แล้วเปลี่ยนทันทีทั้ง **หัวระบบ** (sidebar / topbar มือถือ) และ **หน้าล็อกอิน**

หน้าล็อกอินทำงานตอนยังไม่ล็อกอิน จึงต้องอ่านได้โดยไม่มีสิทธิ์อะไรเลย
→ **แยกเป็นสองตาราง ไม่ใช่สองคอลัมน์**: `branding` (อ่านสาธารณะได้) กับ `app_settings` (เจ้าของเท่านั้น)

เพราะ RLS ของ Postgres คุมได้ระดับ*แถว* ไม่ใช่ระดับ*คอลัมน์* — ถ้าอยู่ตารางเดียวกัน
วันที่มีคนเติมเลขผู้เสียภาษีหรือเลขบัญชีธนาคารลงไป มันจะหลุดออกหน้าล็อกอินทันทีโดยไม่มีใครสังเกต

ต้องมี **ค่าสำรอง**ตอนยังไม่ได้ตั้งชื่อ และตอนโหลดโลโก้ไม่สำเร็จ — หน้าล็อกอินห้ามพังเพราะรูปไม่ขึ้น

### 5.8 "คน" กับ "ผู้ใช้ระบบ" เป็นคนละรายการ

| | คนงาน (`employees`) | ผู้ใช้ระบบ (`profiles`) |
|---|---|---|
| คือใคร | ทุกคนที่มีค่าแรงต้องจ่าย | ทุกคนที่ล็อกอินได้ |
| ล็อกอิน | ไม่ได้ | ได้ |
| role | **ไม่มี** | `owner` / `site_supervisor` |

อยู่หน้าเดียวกัน (`/settings/users`) แต่คนละแท็บ · เจ้าของสร้างได้ทั้งสองอย่าง
คนที่เป็นทั้งสองอย่าง (หัวหน้าโครงการที่กินเงินเดือนด้วย) เชื่อมกันด้วย `employees.profile_id`

**ค่าแรงตั้งรายคนเสมอ** — รายวันหรือรายเดือน และเรตของแต่ละคน อยู่บนแถวของคนนั้น
ไม่มีค่าแรงกลางของระบบ

### 5.9 Audit log
บันทึกด้วย **trigger ที่ระดับฐานข้อมูล** ครอบทุกตาราง ทุก INSERT/UPDATE/DELETE
เก็บ ใคร · เมื่อไหร่ · ค่าก่อน (jsonb) · ค่าหลัง (jsonb) · แก้ไขหรือลบประวัติไม่ได้ · เจ้าของเท่านั้นที่ดูได้

ทำที่โค้ดแอปไม่ได้ เพราะเส้นทางไหนที่ลืมใส่ก็จะหายไปเงียบ ๆ และไม่มีใครรู้ว่าหาย

## 6. รูปสลิป — Cloudflare R2

| หัวข้อ | ค่าที่ตกลง |
|---|---|
| ที่เก็บ | **Cloudflare R2** (ไม่ใช่ Supabase Storage) |
| สิทธิ์เข้าถึง | **bucket ส่วนตัว + presigned GET อายุ 1 ชม.** — ไม่ใช่โดเมนสาธารณะ |
| อัปโหลด | client บีบรูป → ขอ presigned PUT จาก API ของเรา → **PUT ตรงเข้า R2 ไบต์ไม่ผ่าน Vercel** |
| บีบรูป | `browser-image-compression` → WebP 2 ขนาด: **1600px** (ดูเต็ม) + **320px** (รูปเล็กในลิสต์) |
| เก็บใน DB | `object_key` เท่านั้น **ไม่เก็บ URL เต็ม** — ย้ายโดเมน/bucket ทีหลังได้โดยไม่ต้องแก้ข้อมูลเก่า |
| เสิร์ฟ | `<img>` ธรรมดา · **ห้ามใช้ `next/image` แบบ optimize** (โควตา Vercel Image Optimization แยกและบานปลายง่าย) |
| เก็บนาน | **ถาวร ไม่ลบ** — แต่ต้องมีคอลัมน์/หน้าตั้งค่าที่เปลี่ยนนโยบายได้ทีหลัง และโชว์พื้นที่ที่ใช้ไปแล้ว |

**เหตุผลที่เลือกส่วนตัว + presigned:** สลิปโอนมีชื่อคน เลขบัญชี ยอดเงินอยู่ในภาพ
ถ้าเสิร์ฟจากโดเมนสาธารณะ ใครที่ได้ลิงก์ไปจะเปิดได้ตลอดไปและเรียกคืนไม่ได้
ส่วน presigned URL เซ็นด้วย HMAC ในเครื่องเรา ไม่ต้องยิงไปถาม Cloudflare — ไม่ช้าและไม่มีค่าใช้จ่ายเพิ่ม

**สองอย่างที่ต้องไม่ลืม:** R2 ไม่มี RLS สิทธิ์ต้องบังคับเองที่ route handler (หัวหน้าโครงการ A ต้องเปิดสลิปโครงการ B ไม่ได้)
· ต้องมีตัวเก็บกวาดไฟล์กำพร้า — รูปที่อัปแล้วผู้ใช้ปิดแอปก่อนกดบันทึก จะค้างใน R2 ตลอดไปโดยไม่มีแถวใน DB

## 8. อนิเมชั่น

กติกา: **150–380ms · ใช้แต่ `transform` / `opacity`** · ปิดทั้งหมดเมื่อ `prefers-reduced-motion: reduce`

**เส้นโค้งเดียวทั้งระบบ: `cubic-bezier(.22, 1, .36, 1)`** (ease-out-quart — ชะลอตัวเรียบ ไม่เลยเป้า)
ห้ามใช้เส้นโค้งแบบเด้ง/ยืดหยุ่น (`cubic-bezier(.34, 1.56, .64, 1)` และญาติ ๆ) — ของจริงชะลอตัวเรียบ ไม่ดีดกลับ
และบนปุ่มที่กำลัง**กดลง** การเลยเป้าแล้วดีดกลับทำให้ปุ่มรู้สึกเป็นเยลลี่ ไม่ใช่ของแข็ง

| จุด | สิ่งที่เกิดขึ้น | ทำไมถึงคุ้ม |
|---|---|---|
| แถบความคืบหน้า | วิ่งจาก 0 ไล่กันทีละเส้น (`scaleX`) | เป็นจังหวะที่คนอ่านตัวเลขจริง |
| การ์ดสรุปเงิน | ไล่ขึ้นมาทีละใบ ห่าง 50ms | บอกลำดับการอ่านโดยไม่ต้องเขียนอธิบาย |
| ติ๊กคนเข้าโครงการ | เครื่องหมายถูกเด้ง + ยอดค่าแรงวิ่งขึ้นลง | ยืนยันว่าการติ๊กมีผลต่อเงินจริง |
| อนุมัติ/ตีกลับ | แถวเลื่อนออก + ตัวเลขบนเมนูลด | เห็นผลของการกดโดยไม่ต้องโหลดหน้าใหม่ |
| แนบ/ลบรูป | รูปเด้งเข้า-ออก | |
| โทสต์ | เลื่อนขึ้นจากล่าง | ใช้แทน `alert()` เสมอ |
| โหลดรายการ | โครงร่างเรืองแสง → สถานะว่าง | ทุกหน้าต้องมีครบ 4 สถานะ |
