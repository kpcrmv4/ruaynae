**หลักฐาน:** `verify-notify.mjs` (16) — อยู่ใน `npm run verify:all`

**red-test ที่ทำไปแล้ว**
- ตัดเงื่อนไข `new.status is distinct from old.status` ออกจาก trigger →
  **P3-DB-15 แดง**: กดอนุมัติซ้ำได้แจ้งเตือน **2 ใบ** ใส่คนคีย์
  ซึ่งบนมือถือคือกระดิ่งเด้งสองครั้งจากการกดพลาดครั้งเดียว
- เพิ่ม insert policy ให้ `authenticated` → **P3-DB-07 แดง**: หัวหน้าไซต์
  ยิงแจ้งเตือน**ปลอม**เข้ากระดิ่งเจ้าของได้สำเร็จ (201 · +1 แถว)

**สิ่งที่ตารางแถวนี้จับได้ตั้งแต่วันแรก** — `P3-DB-12` แดงในการรันครั้งแรก:
`realtime.messages` ยัง**ไม่มี partition** ของวันนี้เลยสักวัน เพราะบริการ Realtime
ของโปรเจ็คนี้ไม่เคยถูกเรียกใช้ · `realtime.send()` กลืน error ทุกชนิดเป็นแค่
`RAISE WARNING` (อ่านตัวฟังก์ชันได้จาก `pg_proc`) ดังนั้น **แจ้งเตือนทุกใบจะไม่ถูกส่งเลย
โดยไม่มี error ที่ไหน** — trigger รัน · transaction commit · หน้าจอปกติ
· ต่อ websocket เข้าไปครั้งแรกได้ `CHANNEL_ERROR MissingPartition` แล้ว Realtime
สร้าง partition ให้ 5 วันล่วงหน้า หลังจากนั้นทุกอย่างทำงาน
→ **P3-c ต้อง subscribe แบบมี retry** ไม่ใช่ยอมแพ้ที่ `CHANNEL_ERROR` ครั้งแรก

**กฎการติ๊ก** — แถวที่ ID มี `-DB-` `-API-` ต้องมี ID อยู่ใน label ของ check ที่รันได้จริงใน
`scripts/**` · ติ๊กจากความจำไม่นับ · กระทบยอดด้วย `node scripts/verify-matrix.mjs`

**สามอย่างที่เฟสนี้พังง่ายที่สุด**

1. **แจ้งเตือนที่เขียนไว้ใน route** — เส้นทางที่ลืมใส่จะเงียบหายไปโดยไม่มีใครรู้
   เหมือน audit log ที่เขียนในโค้ดแอป · trigger เท่านั้นที่ครอบทุกทางเข้า
   รวมถึง SQL ที่รันมือ และ seed
2. **`0 === 0` อีกรอบ** — "หัวหน้าไซต์ไม่เห็นแจ้งเตือนของคนอื่น" ผ่านได้ทันที
   ถ้าไม่มีแจ้งเตือนอยู่เลย · ทุกแถวที่ตรวจการมองเห็นต้องมีทั้งฝั่ง **เห็น > 0**
   และฝั่ง **ไม่เห็น = 0** ในการตรวจเดียวกัน
3. **กดอนุมัติซ้ำ** — เน็ตช้าแล้วกดสองที · ครั้งที่สองต้องได้ 409 และต้องไม่เกิด
   แจ้งเตือนใบที่สอง · ตรวจที่ **จำนวนแถวแจ้งเตือน** ไม่ใช่แค่ status ปลายทาง

**ยังไม่ทำในเฟสนี้ (อยู่ P7):** web push · badge บนไอคอนแอป · service worker
กระดิ่งในแอปทำงานได้เต็มที่โดยไม่ต้องมีสามอย่างนั้น
